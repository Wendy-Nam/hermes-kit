# 공개 배포 개인정보·비밀정보 점검

이 문서는 공개 ZIP을 만들 때의 최소 공개 경계와 검토 절차입니다. 자동 검사는 알려진 패턴과 위험 경로를 찾는 보조 수단이며, 개인정보나 비밀정보가 전혀 없음을 증명하지 않습니다. 공개 전 사람의 최종 검토가 반드시 필요합니다.

## 공개 경계

배포물은 `build_bundle.py`의 명시적 허용 목록으로만 만듭니다. 런타임 코드, 사용 설명서, 합성 예시, 필요한 오픈소스 라이선스와 출처 고지만 포함합니다. 다음 항목은 넣지 않습니다.

- 계획 문서, 내부 리뷰, 취소된 워크숍 자료, 개인 저장소의 경로·이름·사례
- 실제 `setup.json`, `.env` 계열, 자격 증명·키·인증서·로그·데이터베이스 파일
- `vault`, `profiles`, `userprofiles`, `output`, `results`, 지원 번들, 설치 상태와 로컬 문서 캐시
- 실제 입력·출력, 메시지 내역, 연락처 목록, 고객·회사별 자료, 스크린샷과 녹화물
- 개발 테스트와 그 안의 의도적인 합성 토큰 fixture

`setup.example.json`과 `samples/`에는 합성 데이터와 `example.com` 계열 주소만 사용합니다. MIT 등 제3자 라이선스의 저작권자 표기와 출처 고지는 개인정보처럼 지우지 않습니다. 이는 재배포 조건을 지키기 위한 필수 정보입니다.

## 자동 검사

인터넷에 연결하지 않은 상태에서 공개 ZIP과, 필요하면 별도로 만든 공개 staging 폴더를 검사합니다. 작업 저장소 전체에는 배포 대상이 아닌 개발 자료와 합성 보안 fixture가 있으므로, 저장소 전체가 아니라 실제 공개 경계를 검사합니다.

```bash
python3 build_bundle.py
python3 privacy_audit.py --archive dist/hermes-outbound-kit-0.1.zip
python3 privacy_audit.py --root /path/to/public-staging
```

종료 코드 `0`과 `automated_checks_clear_manual_review_required`는 자동 규칙에서 발견하지 못했다는 뜻일 뿐입니다. `blocked` 또는 종료 코드 `1`이면 공개하지 말고 JSON의 파일·규칙·일치 줄 수를 기준으로 원본을 로컬에서 수정합니다. 보고서에는 일치한 문자열이나 비밀값이 나오지 않습니다. 보고서를 외부로 전달하더라도 파일명 자체가 민감할 수 있으므로 먼저 검토합니다.

검사는 다음 경계를 차단하거나 표시합니다.

- 민감 파일명과 개인 실행 데이터 디렉터리
- 개인키 표식, 알려진 토큰 형태, URL 안의 자격 증명, 비밀값으로 보이는 리터럴 할당
- 개인 이메일·전화번호·사용자 홈 경로
- 사설 네트워크 URL, 내부 작업 경로, 비공개 저장소를 가리키는 흔적
- ZIP 경로 탈출, 심볼릭 링크, 암호화 항목, 예상 밖 바이너리와 크기 한도

스캐너는 차단된 `vault`, 출력, 프로필 등의 하위 파일을 열어보지 않고 경로 자체만 보고합니다.

## 사람의 최종 검토

자동 검사가 통과한 정확한 ZIP을 새 디렉터리에 풀고 다음을 확인합니다.

1. ZIP 파일 목록이 허용 목록과 일치하며 계획·워크숍·테스트·로컬 상태가 없는지 확인합니다.
2. 문서와 예시에서 실명, 약력, 전화, 개인 이메일, 고객·회사명, 비공개 저장소명, 내부 URL 및 실제 메시지를 검색합니다.
3. 이미지·PDF·문서 바이너리가 없어야 합니다. 필요해 추가했다면 화면 내용과 작성자·위치 등 메타데이터를 별도로 검토합니다.
4. 모든 샘플 입력·출력이 합성 데이터인지, 실제 사용자의 문장을 익명화한 것이 아닌 처음부터 만든 fixture인지 확인합니다.
5. 제3자 코드·문서의 라이선스, 저작권 표기, 정확한 출처와 고정 버전을 보존했는지 확인합니다.
6. 검사 이후 ZIP이 바뀌지 않았는지 해시를 기록하고, 그 해시의 파일만 공개합니다.

두 명이 검토할 수 있다면 작성자가 아닌 검토자가 마지막 ZIP을 독립적으로 확인합니다. 의심되는 항목은 공개 목록에서 제외한 뒤 다시 빌드하고 재검사합니다.
